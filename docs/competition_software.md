## 2.3 软件系统介绍

### 2.3.1 软件总体设计

本软件系统以 **ESP32-S3 微控制器** 作为嵌入式主控，搭载 FreeRTOS 实时操作系统，负责协调各软件任务模块的调度与通信。

在任务架构方面，ESP32-S3 通过 FreeRTOS 多任务机制并行管理图形界面渲染、WiFi 网络通信、HTTP/TCP 指令处理、音频语音交互以及电机控制工作流等核心任务。各任务之间通过互斥锁（Mutex）、信号量（Semaphore）和消息队列进行同步与数据交换。

在外部通信方面，ESP32-S3 通过 WiFi AP 模式（SSID: dough_mixer）建立无线局域网，与 PC/云端部署的 **小智 AI 服务端** 通过 WebSocket 长连接进行实时双向通信，同时为触控屏、网页控制面板和微信小程序提供统一的 HTTP REST API 接入点。设备端音频采集与播放通过 I2S 全双工总线连接 INMP441 MEMS 麦克风与 MAX98357A D 类功放模块。

整体软件架构设计重点保证多任务并发下的实时响应能力与控制安全性，通过三端互斥锁机制确保触控屏、网页和小智 AI 三种控制源在同一时刻仅有一端能够操作硬件执行机构，使各软件模块能够稳定协同运行。

### 2.3.2 软件各模块介绍

#### 一、核心工作流引擎模块

核心工作流引擎 `function.c` 是设备端自动化控制的中心模块，负责接收来自各控制源的面团重量参数，按照预设配方比例计算各物料的用量，并分阶段驱动所有执行机构完成全自动和面流程。

该模块内部维护五组配方比例常数（`k_flour`、`k_water`、`k_grain`、`k_yeast`、`k_salt`），均为 `float` 浮点类型以保证计算精度。当任意控制源调用 `weight_work(weight)` 函数时，模块先将面团总重量代入配方公式，通过浮点运算得出各物料的目标值，再统一在最终结果处进行 `(int)` 强制类型转换，避免中间过程的精度截断损失。

工作流程分为四个阶段：Task1 面粉加入阶段，通过 GPIO18 控制面粉磁铁阀开启，同时启动面粉电调（ESC）以 40% 油门运转，根据计算出的 `flour` 时长参数驱动面粉电机；Task2 水泵加水阶段，通过 `ledc_pwm_set_state(1)` 开启 DRV8870 驱动的水泵电机，以流量计脉冲计数替代定时关断，达到目标脉冲数后调用 `ledc_pwm_set_state(0)` 关闭；Task3 研磨与加料阶段，研磨电机（GPIO46 继电器控制）启动后，双舵机按酵母和盐的循环次数交替执行旋转定位、击打下料和归位动作，研磨电机采用间歇工作模式（运行 60 秒 / 停止 30 秒循环）以保证研磨均匀性；Task4 搅拌阶段，启动搅拌电调以 40% 油门持续运转指定时长后熄火。

该模块采用分段顺序执行而非状态机并发的方式设计，目的是确保和面工艺的严格时序——后续阶段必须在前一阶段完成后才能开始，避免加料顺序错误导致的面团质量问题。

**关键输入变量：** `weight`（uint32_t，面团总重量/g）、`k_flour`~`k_salt`（float，配方比例常数）

**关键输出变量：** `flour`（int，面粉电机运行时长/ms）、`water`（int，水泵运行时长/ms）、`grain`（int，研磨运行时/ms）、`yeast`/`salt`（int，加料循环次数）

#### 二、三端互斥控制模块

三端互斥控制模块 `ctl_mutex` 是为解决触控屏（CTL_TOUCH）、网页控制面板（CTL_HTTP）和小智 AI 语音（CTL_XIAOZHI）三方并发控制冲突而设计的同步机制。

在系统运行过程中，用户可能同时通过触控屏点击“启动”按钮，通过手机浏览器发送 HTTP POST 请求，以及通过微信小程序下发小智 AI 语音指令。如果三个控制源各自独立创建电机任务，将导致多组 `fwork()` 同时执行，造成硬件执行机构的控制混乱和机械碰撞风险。

该模块基于 FreeRTOS 互斥信号量（Mutex）实现，对外提供三个核心接口：`ctl_try_acquire(src)` 采用非阻塞方式尝试获取控制权，若当前已有其他源占用则立即返回 `false` 并附带日志记录占用者信息；`ctl_release(src)` 用于任务完成后释放控制权；`ctl_get_owner()` 用于外部查询当前控制权归属状态。

在触控屏路径中，`action_star_mixer()` 函数在创建电机任务前调用 `ctl_try_acquire(CTL_TOUCH)`，若获取失败则在日志中输出警告并直接返回；`action_stop()` 函数在调用 `fstop()` 后执行 `ctl_release(CTL_TOUCH)`。HTTP 路径与小智 AI 路径采用相同的加锁/释放模式。

值得注意的是，该模块采用“非阻塞尝试获取”而非“阻塞等待”策略。这一设计选择的原因是：当和面流程正在执行时（通常持续 5-15 分钟），阻塞等待将导致触控屏 UI 线程或 HTTP 请求超时冻结，用户体验极差。非阻塞策略使得被拒绝的控制源能够立即向用户反馈“系统正忙”的状态信息。

#### 三、DRV8870 水泵 PWM 驱动模块

DRV8870 水泵 PWM 驱动模块 `ledc_pwm` 负责将原有的 GPIO 继电器开关控制升级为基于硬件 PWM 的电机调速控制。

在原设计中，水泵通过 `gpio_set(7, 0/1)` 直接控制继电器通断，仅能实现全速运转或完全停止两种状态，且继电器触点在频繁开关过程中易产生电弧和机械磨损。升级为 DRV8870 电机驱动模块后，通过 ESP32-S3 的 LEDC（LED PWM Controller）硬件外设产生占空比可调的 5kHz PWM 方波，经 IN1/IN2 双路输入控制 H 桥输出，实现水泵电机的无级调速与正反转控制。

该模块采用 LEDC 定时器 0（5kHz, 10-bit 分辨率），通道 3 连接 DRV8870 IN1（GPIO12），通道 4 连接 IN2（GPIO13）。选择 10-bit 分辨率而非更高位宽的原因是：ESP32-S3 的 LEDC 时钟源为 80MHz APB 时钟，当分辨率为 10-bit（1024 个占空比等级）时，理论最高可输出频率为 78kHz，5kHz 可通过分数分频器精确实现；而若选用 13-bit 分辨率（8192 等级），理论最高频率仅为 9.8kHz，无法达到 5kHz，实际输出将远低于预期值。在设计过程中，需严格确认目标频率在所选分辨率下的可达性。

模块对外仅暴露 `ledc_pwm_set_state(int state)` 单一接口：`state=0` 时将占空比设为 0（两路输出低电平，电机关闭），`state=1` 时将通道 0 占空比设为 50%（511/1023），通道 1 保持低电平，电机半速正向运转。内部首次调用时自动完成 `ledc_timer_config` 和 `ledc_channel_config` 的一次性初始化，无需外部手动调用初始化函数。

该设计需要注意 LEDC 通道号的全局唯一性：ESP32-S3 在低速模式（LEDC_LOW_SPEED_MODE）下共有 8 个通道（CH0-CH7），所有通道共享 4 个定时器。同一通道号不能同时分配给两个不同的定时器。本项目中，CH0 已被旋转舵机（Timer2）占用，CH1 被步进电机（Timer1）占用，CH2 被击打舵机（Timer2）占用，CH6/CH7 被面粉和搅拌 ESC（Timer3）占用，因此水泵模块使用 CH3 和 CH4 以避免通道冲突。

#### 四、小智 AI 语音交互模块

小智 AI 语音交互模块 `xiaozhi` 是实现设备端与云端智能服务双向通信的核心软件组件，负责音频采集编码、唤醒词检测、WebSocket 实时通信以及 MCP（Model Context Protocol）设备控制指令的接收与执行。

模块启动时，首先初始化 I2S 全双工音频编解码器（INMP441 麦克风 + MAX98357A 扬声器功放），配置采样率为 16kHz、单声道、Opus 编码、60ms 帧时长。随后加载 ESP-SR 多网络唤醒词引擎模型（"你好小智"），使能唤醒词检测。当唤醒词被触发后，模块进入录音状态，将麦克风采集的原始 PCM 音频经 Opus 编码压缩后通过 WebSocket 实时上传至小智 AI 服务端。

服务端接收到音频流后，依次调用 VAD（语音活动检测）切分有效语音段、ASR（自动语音识别）将音频转为文本、LLM（大语言模型，支持 DeepSeek/ChatGLM）进行意图理解与回复生成、TTS（文本转语音）将回复合成为音频流，整体时延控制在 2 秒以内。对于设备控制类意图，服务端通过 MCP 工具调用机制下发结构化 JSON 指令至设备端，模块内部的 `handle_mcp_command()` 函数解析 `tool` 字段并映射到本地工作流函数。

MCP 指令支持的工具包括：`start_mixer {weight}` 启动和面（映射至 `weight_work()`）、`stop_mixer` 紧急停止（映射至 `fstop()`）、`push_out` 面团推出、`push_back` 面团退回。在执行 `start_mixer` 前，模块会先调用 `ctl_try_acquire(CTL_XIAOZHI)` 获取三端互斥锁，若失败则通过服务端向用户反馈“设备正忙”的语音提示。

I2S 音频总线采用全双工模式：BCLK（GPIO14）和 WS（GPIO16）由麦克风与扬声器功放共享，SD（GPIO17）接收麦克风数据，DIN（GPIO7）输出扬声器数据。全双工模式下仅需 4 个 GPIO 引脚即可同时支持音频输入和输出，相较于分离式接线节省了 2 个 GPIO，为其他扩展外设预留了更多引脚资源。

模块在初始化时创建两个独立 FreeRTOS 任务：`xz_mic` 任务（优先级 4）负责从音频编码队列中取出 Opus 帧并通过 WebSocket 发送至服务端；`xz_ws` 任务（优先级 3）负责 WebSocket 连接的保活轮询与断线自动重连（重连间隔 10 秒）。音频采集和编码由 ESP-SR 和 Opus 库在底层硬件中断中处理，不占用额外的任务栈空间。

#### 五、流量计闭环水量控制模块

流量计闭环水量控制模块用于将传统定时开环加水方式升级为基于 YF-S201 霍尔效应流量传感器的闭环脉冲计数控制方式。

在开环定时控制方式中，水泵运行固定时长后关闭，实际出水量受供电电压波动、水管路阻力变化和水箱液位影响，精度仅约为 ±20%。在闭环计数控制方式中，YF-S201 流量计在 1L/min 流量下输出约 7.5Hz 的脉冲方波（450 脉冲/L），每个脉冲对应约 2.22mL 水量。ESP32-S3 的 GPIO37 配置为上升沿中断输入，在中断服务函数中以 `IRAM_ATTR` 修饰的轻量级计数器累加脉冲数，主循环中通过比较当前脉冲计数与目标脉冲数（目标脉冲 = 目标水量(mL) × 0.45）来触发水泵关断。

中断服务函数放置在 IRAM 中以保证中断响应延迟最小化，且中断内部仅执行 `pulse_count++` 单一操作，避免在中断上下文中调用耗时函数导致系统异常。主循环以 10ms 间隔轮询脉冲计数器，平衡了实时性与 CPU 负载。

该模块的精度瓶颈取决于 YF-S201 传感器的固有分辨率。在 300g 面团（需水约 73mL）场景下，累计脉冲数约 33 个，传感器自身 ±2% 误差叠加单脉冲量化误差（±3.0%），总误差约为 ±5%，相比开环定时的 ±20% 有显著提升。对于 500g 以上面团，总误差可控制在 ±4% 以内，满足面团加水精度要求。若未来需要更高精度（如 200g 小剂量场景），可升级为 YF-S401 传感器（5880 脉冲/L，精度提升约 13 倍），接口引脚完全兼容，无需修改硬件电路。

此外，水泵关断后管路中仍残余少量惯性水流（约 1-2 个脉冲 = 2-4mL），由于该值在传感器固有误差范围内，设计中未采用 PID 控制等复杂补偿策略，而是直接接受该偏差，以降低软件复杂度。

#### 六、触控屏图形界面模块

触控屏图形界面模块基于 LVGL v9 嵌入式图形库和 EEZ Studio 可视化设计工具实现，运行于 ST7789V 驱动芯片的 2.4 寸 SPI TFT 液晶屏（240×320 分辨率）与 FT6336U I2C 电容触摸控制器之上。

LVGL 图形库负责底层渲染引擎，包括图层管理、抗锯齿字体渲染、动画过渡和事件分发。EEZ Studio 提供可视化页面布局设计能力，通过拖拽方式生成 screens.c/ui.c 等页面定义文件，再由 LVGL 引擎加载执行。该设计模式将 UI 布局与业务逻辑分离：EEZ Studio 生成的代码负责页面结构和控件属性，`action.cpp` 用户编写文件负责按钮点击事件的实际业务处理（如调用 `weight_work()`、`fstop()`、`push_and_out()` 等函数）。

UI 主循环在 `app_main()` 中以 10ms 周期调用 `ui_tick()` 函数驱动 EEZ Flow 状态机，处理动画帧更新、属性绑定和事件分发。LVGL 的渲染缓冲区分配为双缓冲模式（LVGL draw buffer），在减少屏幕撕裂的同时将渲染任务与 FreeRTOS 任务调度解耦。

#### 七、HTTP/TCP 网络控制模块

HTTP/TCP 网络控制模块为系统提供基于标准网络协议的远程控制能力，包含两个子模块：

**HTTP 服务器**（端口 80）以 FreeRTOS 独立任务运行，内嵌静态 HTML 网页固件（通过 CMake EMBED_FILES 编译期嵌入），向连接至 ESP32 AP 的客户端提供网页控制面板。同时提供 REST API 接口：`POST /api/start`（传入 JSON `{"weight": N}` 启动和面）、`POST /api/stop`（紧急停止）、`GET /api/status`（返回当前运行状态，JSON 格式）。REST API 设计遵循无状态原则，每个请求独立鉴权（通过互斥锁），不依赖 Session 或 Cookie。

**TCP 指令服务器**（端口 8080）以 FreeRTOS 独立任务运行，监听文本行指令（CR/LF 分隔），支持单客户端串行连接模式（backlog=1）。指令解析器 `wifi_process_cmd()` 采用前缀匹配策略，先匹配较长前缀（如 "MI " 搅拌指令），再匹配较短前缀（如 "M " 步进电机指令），避免误匹配。

HTTP 和 TCP 模块在执行电机启动指令前均需通过 `ctl_try_acquire()` 获取互斥锁，确保与触控屏、小智 AI 控制源之间的操作互斥。
